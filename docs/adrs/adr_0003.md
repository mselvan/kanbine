# ADR-0003: Implement JWT Authentication

## Status
Accepted

## Context
The application currently has no authentication enforcement; `SecurityConfig` permits all requests. To protect API endpoints and support user login, we need a stateless authentication mechanism. JWT (JSON Web Token) is a widely adopted solution that works well with Spring Boot and allows clients to include a token in the `Authorization` header for each request.

## Decision
We will implement JWT authentication with the following components:
- **JwtUtils**: Utility class for generating, parsing, and validating JWT tokens.
- **JwtAuthenticationFilter**: Spring Security filter that extracts the token from the request header, validates it, and sets the authentication in the security context.
- **CustomUserDetailsService**: Implements `UserDetailsService` to load user details (email and password) from the database.
- **AuthController**: Exposes `/api/auth/login` and `/api/auth/register` endpoints for obtaining a token and creating users.
- **SecurityConfig**: Updated to secure all endpoints, permit `/api/auth/**` and Swagger URLs, enforce stateless session management, and add the JWT filter.
- **Dependencies**: Added `jjwt` libraries to `build.gradle`.

## Consequences
### Positive
- **Security**: All API endpoints (except auth and Swagger) require a valid JWT, preventing unauthorized access.
- **Scalability**: Stateless authentication works well in distributed environments.
- **Standardization**: Aligns with common industry practices for REST APIs.

### Negative
- **Complexity**: Introduces additional classes and configuration.
- **Token Management**: Requires handling token expiration and refresh strategies in the future.
- **Testing Overhead**: New security flow adds test cases and potential flakiness.

## Implementation Notes
- Tokens are signed with a secret key defined in `application.properties` (e.g., `jwt.secret`).
- Token expiration is set to 24 hours by default.
- Passwords are stored using BCrypt (`PasswordEncoder` bean).
- Existing services and controllers remain unchanged; they now rely on Spring Security's authentication context.
